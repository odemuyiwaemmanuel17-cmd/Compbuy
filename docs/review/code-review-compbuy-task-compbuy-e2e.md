## Summary

The architecture is sound: one integration seam (`app/db.py`), protocol-based gateway, service-layer
authorization, autoescaping templates, and a schema whose constraints mirror the Python validation.
The review found **two high-impact defects, both now fixed and covered by new tests**, plus several
medium items and two design-level risks that need a product decision rather than a code change.

## What Looks Good

- **Single seam.** Only `app/db.py` imports `supabase`; services depend on `Gateway`/`Query` protocols, which is what made a credential-free suite possible at all.
- **Optimistic concurrency done right.** `OfferService.decide` filters the UPDATE on `status = 'pending'` and treats an empty result as a conflict — no lost-update race, independent of the Python pre-check.
- **Defense in depth on schema.** Check constraints and the partial unique index `offers_one_accepted_per_listing` restate the Python rules, and `test_migration_constraints_mirror_the_python_validation` keeps them from drifting.
- **XSS-safe by construction.** Autoescape is on and proven by `test_html_output_is_escaped_against_script_injection`, which asserts the literal `<script>` never reaches the document.
- **Open-redirect guard** in `safe_next` is tested against `//host`, `https://`, and `javascript:` forms.
- **No secrets in the repo**; `.env` is ignored and `.env.example` carries placeholders only.
- **Blocking I/O is offloaded** and that offload is itself tested.

## Verdict

**Approve with follow-ups.** Both Critical findings are fixed and regression-tested. The two High
items (#3 session revocation, #4 service-role/RLS posture) are architecture decisions that should be
consciously accepted or scheduled, not silently shipped.

### Delivery Gate Recommendation
- **Recommendation**: **Pass for merge to `main`**, conditional on running the migration against a real Supabase project before any user-facing deployment.
- **Blocking reasons**: none for the code itself.
- **Open decisions to record**: session-revocation window (7 days) and service-role RLS bypass.

### Design Risks Needing a Decision

1. **Session revocation latency.** Options: (a) accept a 7-day window for an MVP; (b) store the access-token expiry in the session and, once passed, call `auth.refresh_session(refresh_token)` — clearing the session if refresh fails — bounding staleness to ~1 hour; (c) shorten `SESSION_MAX_AGE_SECONDS`. (b) is the correct answer and is a contained change.
2. **Service-role posture.** Options: (a) keep service-role + Python filtering (current); (b) for user-scoped reads, build a per-request Supabase client from the stored access token so RLS enforces ownership in the database as well. (b) restores true defense-in-depth at the cost of one client per request and a token-forwarding RLS design.
